# Repo Orientation: Hokie Trade

> Generated by orient. Re-run to update.

## One-line purpose
A Virginia Tech–only peer-to-peer marketplace prototype — a React Native/Expo app that demonstrates the sign-up, search-by-course, message-seller, and rate-the-trade flow for textbooks, dorm gear, and peer services.

## Primary language(s)
TypeScript (React Native via Expo SDK 57). No test framework and no linter are configured.

## Pipeline / workflow stages
There is no data pipeline here — the "flow" is a user journey through screens held in React state:

1. **Boot** — `index.ts` hands `App.tsx` to Expo's `registerRootComponent`.
2. **Screen dispatch** — `App.tsx` keeps a `screen` state and early-returns a different block of JSX per screen value.
3. **Email gate** — `login` → `verify`: the email must end in `@vt.edu`, any 6 digits then pass.
4. **Browse** — `browse` filters the in-memory `listings` array by the `query` text and lists matching cards.
5. **Detail** — `detail` shows the tapped listing plus a hardcoded "verified" seller row.
6. **Negotiate** — `thread` shows the `messages` state and a suggested safe meetup spot; sending appends to state and a scripted reply arrives after 600 ms.
7. **Rate** — `rating` sets a local star count and returns to browse. Nothing is saved, so a reload resets everything.

## Core concepts
**Screen state machine**: There is no navigation library and no router. `App.tsx` declares `type Screen = 'login' | 'verify' | 'browse' | 'detail' | 'thread' | 'rating'` and renders exactly one screen block based on a single `screen` state value. Every "navigation" is a `setScreen(...)` call, and several screens also require `activeListing` to be non-null.

**In-memory mock data**: The `listings` array (3 hardcoded items, top of `App.tsx`) and the `messages` state are the entire data layer. There is no Firestore, no fetch, no AsyncStorage — the prototype resets on every reload. `SYSTEM.md`'s `users`/`listings`/`messages` collections describe the intended persistence layer, which does not exist in code.

**Simulated trust features**: The trust story is faked in three places rather than enforced: the `@vt.edu` suffix check in `handleSendCode`, the hardcoded "✓ Verified @vt.edu" seller row on the detail screen, and the fixed "Newman Library, main entrance" meetup spot on the thread screen. Ratings are stored in a `rating` state value that is never persisted or displayed again.

**Course agent scaffold**: The repo is also a CS3704 workspace. `.opencode/` holds the agents, skills, and scripts; `baker.yml` records how they were installed; `PHASE.md` and `docs/` are course-owned and will be overwritten as phases are released, so don't build on them.

## Common gotchas
1. **`SYSTEM.md` does not describe this codebase.** It specifies Next.js, Tailwind, Firestore, and Firebase Auth; the running app is React Native/Expo with in-memory data. `README.md` says as much ("Our design documents describe the full system we plan to build"). Reading `SYSTEM.md` as documentation of the current code will send you looking for files that don't exist.
2. **`AGENTS.md` says routes live in `src/app/`, but there is no `src/` directory here.** That section is the generic Expo/Expo-Router guidance from the course template. This prototype has no router at all — screen changes are conditionals in `App.tsx`.
3. **A blank screen means `activeListing` is null.** The final `return null` at the bottom of `App.tsx` is reached whenever `screen` is `detail`, `thread`, or `rating` but no listing was selected. If you add a new entry point to those screens, you must set `activeListing` too.
4. **Search is a raw substring match, not course-aware.** `filtered` compares the query against `l.course` and `l.title` with `includes`, so "CS 3704" matches but "CS3704" and "3704" return nothing. Course-number search in `SYSTEM.md` assumes an exact `where("courseNumber", "==", ...)` query, which is a different behavior again.
